# Parité entre universités

Tafac sert plusieurs universités avec le même code. Ce qui est ajouté pour l'une ne doit ni casser ni changer les autres, sauf intention explicite. Cette liste sert de garde-fou : un agent la relit avant chaque commit fait dans une session Claude Code (hook `PreToolUse` dans `.claude/settings.json`). Elle se complète au fil des cas rencontrés. Elle couvre aussi la parité entre le site et l'appli de bureau (dernière section) : le même CSS sert les deux, avec des variantes.

Universités à vérifier : **toutes celles du dépôt au moment du commit**, pas une liste figée. Chaque dossier de `universities/` est une université (`shared.js`, `client.js`, `server.js`), les `example-*` compris, plus `universities/neutral.js` (la page sans université). Une université ajoutée entre-temps est donc vérifiée comme les autres. Pour chacune, ses particularités se lisent dans sa config : quelles `features` sont actives, quelles clés elle définit ou non, quelles valeurs elle donne aux clés qui choisissent un fournisseur.

## Ce qui bloque un commit

1. **Comportement non conditionné** : du code partagé (`server/`, `src/`, `*.js` à la racine) change pour toutes les universités ce qui ne devait concerner qu'une seule. Toute particularité passe par une clé de config (`universities/<id>/*.js`) dont l'absence garde le comportement d'avant pour les autres.
2. **Clé de config sans défaut** : une nouvelle clé lue sans repli (`config.x.y` qui casse si `x` manque) alors que d'autres universités ne la définissent pas.
3. **Chemin d'un autre fournisseur cassé** : un changement touche une branche choisie par la config sans vérifier les autres valeurs. Toute clé de config qui sert à choisir un comportement en est une, y compris celles ajoutées après l'écriture de cette liste. Pour la trouver, chercher dans le code modifié les lectures de `universityConfig.*`, `FEATURES.*` et `features?.*`, puis comparer les valeurs de chaque université. Exemples connus :
   - portail : `auth.portal` (`'uportal'` par défaut, `'drupal'`) ;
   - second facteur à la connexion : `auth.mfa` (absent = aucune étape de code, `'esup-otp'`) ;
   - planning : `planning.api` (`'portal-rest'`, `'tempo'`, absent = Planning GWT), `planning.personal` ;
   - Moodle : `moodle.casLoginPath` (CAS) ou Shibboleth par défaut ;
   - mail : `mail.provider`, `mail.page` ;
   - notes : `features.grades` (vrai, faux ou `'disabled'`) ;
   - `features.*` en général : un widget, une route ou une entrée de menu doit rester masqué quand sa feature est absente.
4. **Mode démo cassé** : chaque route qui appelle un service universitaire doit répondre au compte démo avant tout appel réseau (`isDemoSession`), pour toutes les universités qui ont `features.demo`.
5. **Forme des données divergente** : deux fournisseurs d'une même donnée doivent rendre la même forme au frontend (événements de planning, `account`, layout d'applications, mails, échéances). Un champ ajouté pour l'un est optionnel (`null` ou absent) pour les autres, et le frontend le gère.
6. **Clé de stockage** : une clé `localStorage` existante est renommée (interdit), ou une nouvelle clé propre à une université n'est pas déclarée dans `src/universityStorage.js` (et, si c'est un réglage, dans `src/settingsTransfer.js`, `src/components/WelcomeFromLent.jsx`, `src/components/debug/debugUtils.js`).
7. **Données personnelles** : identifiants, numéro étudiant, nom, notes ou emploi du temps réels dans un fichier commité.
8. **Session expirée devinée** : seul le CAS dit qu'une session est morte (`server/sessionExpiry/` : sa page de connexion demandée avec le TGC montre le formulaire du mot de passe). Une route qui appelle un service de l'université finit son `catch` par `answerIfSessionExpired(req, res, error)` avant sa propre erreur ; aucun code ne déconnecte sur un statut, un message d'erreur ou une page d'un service (401 d'ADE, `{ redirect }` de ScoDoc, page de connexion de Moodle) : une panne, un délai dépassé ou un 5xx gardent la session. La page ne déconnecte que sur l'en-tête `X-Tafac-Session: expired` (`src/sessionSignal.js`), jamais sur un échec, et n'ajoute pas d'écran « Session expirée » propre à un service.

## Ce qui mérite un avertissement (sans bloquer)

- **Visuel** : une taille ou une mise en page qui dépend de la forme d'un logo (`logoShape` `'wide'`/`'square'`), d'une photo de fond, d'un lockup, d'un nombre d'éléments, doit rester correcte pour chaque université (page de connexion, accueil « Compatible avec », sidebar, en-tête, mode sombre avec logo inversé).
- **Textes** : un texte qui nomme un service (« ADE », « ScoDoc », « Moodle ») alors qu'une université en utilise un autre (`planning.providerName`).
- **Tutoiement / vouvoiement** : un nouveau texte qui s'adresse à l'étudiant (« tes notes », « Choisis… », « Reconnecte-toi ») écrit en dur dans une seule forme. Il passe par `r('forme tu', 'forme vous')` de `src/register.js`, appelé au moment de l'affichage (pas dans une constante de module : elle garderait le registre du chargement ; un objet de libellés prend des getters). Le registre vient de `register` dans la config de l'université (`'vous'` partout, `'tu'` pour l'établissement `iutlan` de Rennes) : une université sans `register` vouvoie. Les textes de `branding` et de `universities/neutral.js` sont en « vous » ou impersonnels, le serveur reste impersonnel.
- **Documentation** : une nouvelle clé de config absente de `docs/ADDING_A_UNIVERSITY.md`.
- **Tests** : une nouvelle logique pure sans test, ou un test qui ne couvre qu'une variante.
- **Signature des mails** : un établissement ou un logo ajouté à `client.js` (`establishments.byId`, `branding.logo`) sans son entrée dans `server.js › mail.signature` (et son PNG rendu par `scripts/render-mail-logos.mjs`) n'apparaît pas dans la signature des mails envoyés. De même, `mail.signature.showLogin` doit avoir la même valeur dans `client.js` et `server.js` (une constante de `shared.js`) : sinon le composeur montre une ligne « Identifiant » que le mail envoyé n'a pas, ou l'inverse.
- **Noms d'enseignants du planning** : chaque fournisseur les écrit à sa façon (ADE « M. Lemoine », « LEMOINE Thomas », plusieurs joints par « - » ; TEMPO « Martin C. », souvent aucun). Du code qui lit `teacher` d'un événement (suggestions de destinataires, `src/teacherRecipients.js`) doit couvrir chaque forme et l'absence de nom, sans jamais deviner une adresse.
- **`devOnly`** : une université encore en `devOnly: true` qui reçoit une fonctionnalité annoncée comme publique.

## Web et appli de bureau

L'appli de bureau (`src-tauri/`, `docs/DESKTOP.md`) affiche la même page que tafac.fr, avec des variantes CSS posées sur `<html>` par `src/desktopApp.js` :

- `data-desktop-app` (toute appli de bureau) : flèche au lieu de la main sur les boutons, pas de rebond au défilement (sur tout ce qui défile sous macOS, sur la page seulement ailleurs : sous Windows, `overscroll-behavior: none` sur un widget empêcherait la molette de passer à la page), liens et images non déplaçables ;
- `data-desktop-macos` (macOS) : pas de barre de titre (les boutons de la fenêtre dans le coin haut de la sidebar), sidebar collée aux bords et transparente sur la matière système, panneaux de droite (lecteur de mail, « Salles et personnels ») collés au bord droit dans leur couleur, composeur plein écran sous les boutons de la fenêtre, colonne de contenu décalée par une marge (`.app-column`), sidebar repliée à 84px au lieu de 72 (`src/sidebarWidth.js`), bande de 52px en haut qui déplace la fenêtre (`src/desktopWindowDrag.js`), largeur minimale 1024px (jamais la mise en page téléphone).
- `data-desktop-windows` (Windows 11, posé seulement si `src-tauri/src/window.rs` a mis le Mica : `window.__TAFAC_MICA__`) : mêmes règles de sidebar que macOS (transparente sur le Mica, collée aux bords, `.app-column` décalée), sans trait à droite de la sidebar. La barre de titre est dessinée par-dessus la page (`tauri-plugin-decorum`) : bande de 48px (`--desktop-titlebar-height`) sur le Mica, « Tafac » à gauche, les trois boutons de la fenêtre à droite (138px). La sidebar commence sous la bande, `.app-column` aussi, sur un calque plein au coin haut gauche arrondi (8px) avec un trait de 1px ; les panneaux de droite et le composeur plein écran commencent sous la bande. La fenêtre peut descendre sous 1024px : la mise en page téléphone prend la fenêtre sous la bande, sans marge ni coin.

Les règles sont à la fin de `src/overrides.css`. Windows et Linux gardent leur barre de titre, une sidebar flottante et la mise en page téléphone sous 1024px.

Bloque un commit :

- **Variante non conditionnée** : du CSS ou du JS propre à l'appli qui s'applique aussi au site (pas derrière `:root[data-desktop-app]`, `:root[data-desktop-macos]`, `isDesktopApp()` ou `isMacDesktopApp()`), ou l'inverse : un changement pour le site qui défait une règle de l'appli.
- **Mise à jour contournée (appli)** : dans `src/main.jsx`, un appel au serveur (`/__ent_auth`, `/__ent_proxy`) ajouté avant la réponse de `startDesktopUpdates()`, ou du code propre aux mises à jour (`src/desktopUpdate.js`, `/__desktop/update/*`) qui s'exécute hors de l'appli. Une version trop ancienne affiche « Mise à jour nécessaire » sans rien demander à l'université ; le site, lui, ne connaît pas ces routes.
- **Connexion gardée (appli)** : l'appli garde l'identifiant et le mot de passe dans le trousseau et se reconnecte seule (`src-tauri/src/signin.rs`). Elle oublie ce qu'elle garde sur `code: 'login_refused'` de `POST /__ent_auth/login` (`server/casLogin/refusal.ts`) ou un code `mfa_*`, et le garde sur toute autre erreur. Un nouveau chemin de connexion (autre portail, autre fournisseur d'identité, autre second facteur) donne `login_refused` seulement quand l'université a refusé l'identifiant ou le mot de passe, jamais sur une panne, un délai dépassé ou un 5xx (l'appli oublierait le mot de passe d'un étudiant à chaque coupure), et ne laisse jamais une connexion `quiet: true` envoyer un code par SMS ou mail. Côté page, une déconnexion que l'étudiant n'a pas demandée (session expirée) passe `logoutFromEnt({ expired: true })` : sans cela l'appli oublie le mot de passe. Le compte démo n'est jamais gardé.
- **Accroche renommée** : une classe ou un attribut sur lequel s'appuient les règles de l'appli (`.sidebar-panel`, `.sidebar-panel--compact`, `.sidebar-peek`, `.app-column`, `main`, `data-tauri-drag-region` sur les `<aside>` de la sidebar, `--sidebar-width`, `.mail-reader-panel`, `.side-panel`, `--mail-reader-width`, `--side-panel-width`, `.mail-composer.is-fullscreen`) renommé ou déplacé sans mettre à jour `src/overrides.css` et `src/desktopWindowDrag.js`.

Mérite un avertissement :

- **Sous la sidebar (macOS, Windows 11)** : un fond opaque qui passe sous la sidebar (bande pleine largeur, ombre étalée, élément fixe sur toute la fenêtre, fond sur `html`, `body`, `main` ou le conteneur du tableau de bord) cache la matière système. Ce qui doit aller d'un bord à l'autre s'arrête au bord de `.app-column`.
- **Sous la barre de titre (Windows 11)** : rien de cliquable ni de lisible dans les 48px du haut de la fenêtre (`--desktop-titlebar-height`), surtout à droite sous les trois boutons de la fenêtre. Un élément fixé en haut (`top: 0`, `top-3`) commence sous la bande.
- **Plein écran (macOS)** : un élément qui couvre toute la fenêtre (comme le composeur plein écran) commence à 52px du haut, sous les boutons de la fenêtre.
- **Coin des boutons de la fenêtre (macOS)** : rien de cliquable ni de lisible dans les 52px du haut de la sidebar, ni sous les boutons quand elle est repliée (84px). Une forme qui suppose la sidebar flottante (coins arrondis, marge de 12px, ombre, position `top-3 left-3`) doit avoir sa variante collée.
- **Bande du haut (macOS)** : dans les 52px du haut de la fenêtre, un appui sur ce qui n'est pas reconnu comme cliquable déplace la fenêtre. Un élément cliquable placé là est un `button`, un `a`, un rôle ARIA interactif, a un `tabindex` ou la classe `cursor-pointer`.
- **Contraste sur la matière (macOS, Windows 11)** : le texte et les icônes de la sidebar se lisent sur la matière système, claire ou sombre selon le thème de l'app (`src/desktopWindowTheme.js`) et teintée par le bureau derrière la fenêtre. Pas de couleur qui suppose le fond plein de la sidebar du site.
- **Curseur** : une nouvelle règle `cursor: pointer` plus spécifique que celle de `data-desktop-app` remet la main dans l'appli.
- **Menu de l'appli** : une page ajoutée à la sidebar (`buildNavItems`) arrive seule dans « Aller » ; une nouvelle recherche ou actualisation propre à une page répond à `onDesktopCommand` (`src/desktopMenu.js`) et se déclare dans l'état envoyé par `App.jsx`, sinon l'entrée du menu reste grisée.
- **Mises à jour (appli)** : « Mise à jour prête » est dans le pied de la sidebar, au-dessus du compte (`DesktopUpdateRow` ; repliée, `CompactDesktopUpdateButton` dans `data-sidebar-foot`) : sous 236px de large, son bouton passe sous le texte. « Mise à jour nécessaire » et la note du menu sont dans une racine à part (`DesktopUpdateLayer`, `z-[80]` et `z-[70]`, montée par `src/main.jsx` avant `App`) : un élément plein écran placé au-dessus les cacherait, et leurs textes restent impersonnels (ni « tu » ni « vous » : l'université n'est pas encore connue). Ils se vérifient en clair et en sombre, sur la matière de la sidebar comme sur le fond plein.
- **Impression (appli)** : un nouvel élément fixe ou un nouveau panneau se masque dans le `@media print` de la fin de `src/overrides.css`, sinon il s'imprime.
- **Largeurs** : une mise en page qui ne marche qu'à partir de 1024px ou qu'en dessous se vérifie aussi pour l'appli Windows/Linux, qui descend à 380px.
- **Vue de Moodle (appli)** : « Moodle » est une page de l'appli seulement (`page: 'moodle'` dans `buildNavItems` derrière `isDesktopApp()`), un lien ailleurs. Sa vue est native, au-dessus de tout ce que la page dessine : un élément qui passe sur son emplacement (feuille, menu, note, panneau) n'est vu que si `isSlotCovered` (`src/desktopMoodle.js`) le reconnaît, soit par son rôle (`dialog`, `alertdialog`, `menu`, `tooltip`, `listbox`), soit parce qu'il reçoit les clics à cet endroit (`pointer-events: none` le laisse derrière la vue). Ce qu'elle peut charger vient de la config serveur de l'université (`server/moodleView/policy.ts` : hôtes du relais, `moodle.signInDomains`, `launch.allowedDomains`) : un service de connexion absent de cette liste part dans le navigateur. La tuile de Moodle ouvre cette page (`src/moodlePortalApp.js`) et sort donc des favoris de la sidebar, comme celles des autres pages.
- **Habillage de Moodle (appli)** : `src-tauri/src/moodle_style.css` vise les classes de Moodle (Boost, Bootstrap 4 en Moodle 4.x comme à Rennes, Bootstrap 5 en Moodle 5 comme à Rennes 2), jamais un thème d'université (`kairos`, `rennes2`) : une règle qui ne prend pas chez l'un se corrige avec le sélecteur de Moodle de même poids, pas avec le nom du thème. Seulement la surface (couleurs, polices, coins) : rien qui place ou dimensionne, sauf la colonne `limitedwidth` élargie. Une couleur de l'appli ajoutée à la vue passe par `MOODLE_THEME_TOKENS` (`src/desktopMoodle.js`) et `THEME_TOKENS` (`moodle_style.rs`), les deux listes ensemble. Se vérifie en clair et en sombre : un fond clair que Moodle peint sans couleur de texte devient illisible en sombre.
- **Pages gardées (appli iOS)** : dans l'appli iOS une page visitée reste montée, cachée derrière les autres (`src/keptPages.js`, `docs/IOS.md`), là où le site et l'appli de bureau la démontent en la quittant. Dans une page (`HomeDraftPage`, `GradesPage`, `PlanningPage`, `AssiduityPage`, `MailPage` et tout ce qu'elles affichent), avec `src/pageVisit.js` : une horloge ou un rafraîchissement périodique s'arrête quand la page est cachée (`usePageShown`, `usePageInterval`) ; ce qui se faisait « au montage » pour une arrivée (statistique, donnée relue, demande « ouvre ceci » lue une fois) répond aussi à un retour (`usePageVisit`, `usePageReturn`) ; un `ResizeObserver` ou `IntersectionObserver` qui écrit un état ignore la page cachée, où tout mesure 0 (`isInHiddenPage`, `src/keptPages.js`) ; une feuille, un menu ou une bulle rendus dans `<body>` (`createPortal`) se ferment avec leur page (`useClosedWithPage`, déjà dans `useHistorySheet`, `Dropdown`, `ContextMenu`, `CardInfoTip`), sinon ils restent au-dessus de la page suivante. Plusieurs pages sont dans le DOM en même temps : pas de `document.querySelector` qui suppose une seule page montée.
- **Haut de « Accueil » : deux composants** : sous 1024px (`usePhoneViewport`, la mise en page téléphone : téléphone et tablette) c'est `HomePhoneHeader` (photo fondue, logos, compte, icônes cliquables), au-dessus c'est le bandeau de `HomeDraftPage` sous la barre du haut (`AppHeader`, cachée sous 1024px). Ce qui s'ajoute au haut de la page (une annonce, un bouton, une info du compte) va dans les deux. La déconnexion n'est plus dans l'en-tête sous 1024px : elle est dans Réglages › Compte. Dans l'appli iOS les logos de l'en-tête ne sont pas affichés.
- **Barre d'état (appli iOS, téléphone)** : la page passe derrière la barre d'état (`src/overrides.css`, « iOS app · status bar » ; `docs/IOS.md`). `--status-bar` vaut la hauteur de la barre dans l'appli iOS et 0 partout ailleurs, `--app-h` la hauteur d'écran sous la barre. Une feuille ou un dialogue se dimensionne avec `var(--app-h)`, jamais `100dvh` ; ce qui colle en haut d'une page colle à `top: var(--status-bar)` ; un dialogue centré utilise `.weather-modal-backdrop` (qui reçoit la hauteur de la barre en plus). Un nouvel écran hors tableau de bord commence sous la barre par la règle de `main`, ou étend sa propre couleur derrière comme `.login-right-panel`.
- **Verre du système (appli iOS, téléphone)** : les contrôles du chrome d'une page (pilules et boutons ronds d'un en-tête, d'une barre flottante) sont en verre du système (`src/iosGlass.js`, `src-tauri/plugins/glass`, `docs/IOS.md` « Glass »). Un nouveau contrôle d'en-tête ou de barre le devient avec `data-ios-glass` sur lui, ou sur sa rangée (elle prend alors chaque pilule que la page y dessine : `.material`, `.lent-button` — verre teinté de sa couleur —, `.button-group`, bouton à fond) ; `data-ios-glass="off"` l'en sort. Jamais dans le contenu (carte, ligne de liste, widget), une feuille, un dialogue ou un menu, ni pour un champ de texte. Le verre montre une image du contrôle peinte par la page (`src/iosGlassPaint.js`) : texte sur une ligne, icônes `<svg>` en ligne, photo, fonds unis et filets en `::before` ; pas un dégradé, une ombre, ni une icône stylée par des classes dans son SVG. L'appli le déplace seule avec le défilement, selon trois règles (`fixed`, `sticky`, `page` : `controlTop`, `src/iosGlassModel.js`) : un contrôle dans une zone qui défile seule, déplacé par du JavaScript (glissé au doigt), tourné, ou sous une animation autre qu'un déplacement, une échelle et un fondu simples, garde le dessin de la page. Un contrôle qui défile avec la page ne doit pouvoir passer que sous le voile de la barre d'état, pas sous un en-tête collant (le verre est au-dessus de toute la page). Dans un contrôle, une animation sans fin n'est rendue que pour une icône qui tourne et pour `.loading-spinner`. Ne pas masquer soi-même un contrôle marqué par `opacity: 0` en restant cliquable : le verre lit cette opacité.
- **Menu contextuel et listes déroulantes (appli iOS)** : `ContextMenu` et `Dropdown` deviennent le menu du système (`src/iosMenu.js`, `src/iosMenuItems.js`). Une nouvelle propriété d'élément de menu doit y être traduite, ou faire rester le menu sur celui de la page (`canBeNative`, comme `labelStyle`).
- **Fenêtre à deux vues (appli)** : une fois la vue de Moodle créée, `get_webview_window("main")` et `webview_windows()` de Tauri ne rendent plus la fenêtre principale. Le code Rust passe par `window::page` et `window::pages` (`src-tauri/src/window.rs`).
- **Routes passées à tonAPI (site et applis)** : `GET /__ent_auth/session`, `GET /__ent_auth/account` et `GET /__ent_auth/moodle/deadlines` de Rennes sont répondues par tonAPI quand la session vit, sur le site comme dans les applis (`back/crates/tafac-gateway`, `docs/DESKTOP.md` « tonAPI »). Un champ ajouté, renommé ou retiré dans ces réponses de `server/entAuthApp.js`, ou un champ de `account` que la page lit en plus (`src/App.jsx`), se reporte dans le traducteur de la route (`translate/session.rs`, `translate/account.rs`, `translate/moodle_deadlines.rs`) et ses tests ; de même pour les règles des échéances Moodle (fenêtre, nombre d'éléments, retards gardés, lien par le relais). Une nouvelle route de `server/entAuthApp.js` s'ajoute à la table `routes.rs` (un test la réclame). Le format du cookie de session (`server/sessionCookie.js`) est lu aussi en Rust (`session/cookie.rs`) : un changement casse `tests/sessionCookie.test.js` et les tests du crate ensemble, sur le même cookie d'exemple. Une route dont tonAPI ne peut pas rendre la réponse exacte de Node reste à Node.
- **Téléchargements (applis)** : dans les applis, la vue web ne télécharge pas une adresse de l'appli (`tafac://`), seulement un blob ou un lien `data:`. Un nouveau fichier à télécharger se fait comme les autres : un blob construit ou récupéré par la page (`fetch`, puis `<a download>` sur `URL.createObjectURL`), ou un lien `<a download>` vers un fichier de l'appli, que `src/desktopDownloads.js` (`downloadFile`) fait passer par un blob. Le bureau l'enregistre (panneau d'enregistrement), l'iPhone le donne à la feuille de partage (`src-tauri/src/ios_downloads.rs`). Jamais `window.open` ni une navigation vers le fichier : dans l'appli iOS, le fichier remplacerait la page.
